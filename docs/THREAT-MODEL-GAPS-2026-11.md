# Threat-model gaps from the h4cker / OWASP checklists

h4cker's README names no Android, messaging or API section (only `cybersecurity-domains/`:
crypto, application security, cloud). The checks below come from the standard OWASP
MASVS/MASTG and API Top 10 lists it points at, compared against this repo on 2026-11-04.
Each item says what was checked. Candidates that turned out to be covered are at the bottom.

Status: **open** = a real gap in code or docs; **verify** = needs a test, not yet shown to be a bug.

| # | Check | Status | Evidence | Suggested action |
|---|---|---|---|---|
| 1 | Harvest-now-decrypt-later (post-quantum). Olm and X25519 sealing are not PQ-safe, and the adversary model includes a state actor who records traffic. Google Quantum AI (arXiv 2603.28846, Mar 2026) estimates 256-bit ECC keys breakable with ~1,200 logical qubits; realistic window for Clairix content recorded today is the 2030s. | open (docs) | No mention in `docs/*.md` or `SECURITY.md`; sealing uses X25519 + ChaCha20-Poly1305 (`comms-crypto/src/lib.rs`); evidence signs with ECDSA P-256 (`ReportSigning.kt`) | Plan Format 4: X25519 + ML-KEM-768 hybrid sealing (RustCrypto `ml-kem` or formally verified libcrux); dual ECDSA P-256 + ML-DSA-65 / SLH-DSA evidence signatures anchored to RFC 3161 or OpenTimestamps; add `cargo-fuzz` targets for envelope and bundle parsers (no `fuzz/` dir currently in `comms-crypto`). PQ implementation bugs (DEF CON 34 Krasnov): Rust + vodozemac avoids memory-corruption class; run `dudect`-style timing checks when PQ code lands. |
| 2 | Invite page `/i` had no CSP or framing protection. | fixed in #65 | Was: only content-type, cache-control, referrer-policy, nosniff in `comms-worker/src/index.ts` | Done: CSP by hash, `frame-ancestors 'none'`, `X-Frame-Options: DENY`. |
| 3 | Deep-link input: `https://clairix.app/i` and `clairix://invite?c=…` are BROWSABLE. Is the payload parsed defensively and confirmed by the user before acting? | verify | Manifest lines ~95-108 | Fuzz the invite parser; confirm no action happens without a tap. |
| 4 | Relay-chosen federation targets (SSRF). | checked, no bug | `relayOrigin()` requires https, port 443, a non-IP name, no `.local/.internal`; `forward()` and `fetchRelayKey` both use `redirect: "manual"`. A name resolving to a private IP is not reachable from a Cloudflare Worker. | Keep as is; retest if the relay is ever self-hosted on a network with private hosts (`selfhost/`). |
| 5 | Replay / reorder of relay requests. | checked, covered | Requests carry a ±5-minute timestamp, a single-use nonce, method, path and body hash (`auth.ts`); `relay.test.mjs` covers replay. | None. |
| 6 | Dependency pinning of Rust crates for audits: `cargo-audit` runs, but RustSec "unmaintained" advisories and `cargo vet` are not in the threat model. | open (process) | CI has `cargo-audit`, `npm-audit`, `dependency-review` | Add `cargo deny` / `cargo vet` or document why not. |
| 7 | Root / hooking detection (Frida, debugger). Commodity bypass stack (KernelSU Next + Shamiko + SUSFS + TrickyStore + leaked `keybox.xml`) now forges key attestation and defeats all user-space integrity checks. `KeyAttestation.kt` does not check Google roots or revocation (see gap 13). | open, medium | FLAG_SECURE + `WindowShield.kt` remain valid against non-rooted adversaries. The attestation bypass means evidence reports can be fabricated on a rooted device with a valid-looking attestation chain. | Out of scope per "no compromised OS" for user-space checks; document explicitly. ## New gaps from DEF CON 34 research (2026-11-10)

| # | Check | Status | Evidence | Suggested action |
|---|---|---|---|---|
| 11 | Federation Sybil enumeration. `FED_LOOKUPS_PER_MINUTE = 120` is per-origin. Wildcard DNS (`*.attacker.tld`) generates unlimited distinct origins; each gets a fresh bucket. Full 900M-number space enumerable in ~2 hours with no enrollment secret. Same flood exhausts `KEY_FETCHES_PER_MINUTE = 30`, denying service to legitimate relays. | open | `federation.ts` `FED_LOOKUPS_PER_MINUTE`; `index.ts` line 361; `federationPolicy` defaults to `"open"` | Rate-limit by registrable domain (eTLD+1) instead of full origin; add per-domain lifetime cap on unique targets; separate key-fetch allowance so hostile domains cannot exhaust it; fix is in `federation.ts` + `index.ts`. |
| 12 | No lifetime per-account lookup cap. `LOOKUP_LIMIT_PER_MINUTE = 30` has no daily or lifetime ceiling. With invite chaining (20 invites/hr), one attacker grows to ~9,261 accounts in 3 days; at 43,200 lookups/day each the full space falls in ~2 more days. Registration is IP-limited but Tor bypasses that. | open | `mailbox.ts` line 196 `LOOKUP_LIMIT_PER_MINUTE`; invite logic | Per-account HyperLogLog / hashed set of unique targets in a 30-day window; count 404 results with a tighter separate cap; cap invite subtree depth, lifetime, and require account age before invite rights activate; flag subtrees with high 404 ratios. |
| 13 | `KeyAttestation.kt` does not verify Google attestation roots or revocation. TrickyStore + leaked `keybox.xml` produce a chain accepted as valid. Evidence reports and `PhoneHealthMonitor` verdicts can be forged on a rooted device. | open | `android/.../analysis/KeyAttestation.kt` (no root-CA or revocation check visible) | Bundle Google attestation root public keys and check chain against them offline; ship a snapshot of the Google attestation revocation list and refresh over Tor; flag `revoked key` and `chain not rooted at Google` as HIGH in `PhoneHealthMonitor`. |
| 14 | `sealingPrekey.created` timestamp in lookup responses leaks device activity. Sealing prekey rotates weekly; timestamp tells anyone calling `/v1/lookup` whether the target's device was active in the last 7 days — a surveillance oracle for a stalker monitoring a victim's number. | open | `index.ts` lookup response; `CommsModel.kt` line 296 | Drop `sealingPrekey.created` from the lookup response; the relay can enforce key freshness internally without disclosing creation time. |
| 15 | `listed = true` is the default, so users are enumerable by anyone who can call `/v1/lookup`. Combined with gaps 11 and 12, the full active population can be listed. | open | `CommsConfig.kt` line 26; `CommsModel.kt` line 296 | Ship `listed = false` as default or require the QR pin flow for first contact; audit all lookup paths to return a consistent 404 for absent and unlisted numbers. |
| 16 | BLE tracker detection uses single-field matching (OUI or CID alone). Single-field matching triggers false positives from phones running vendor apps (Apple CID `0x004C` alone hits every iPhone; Meta CID `0x0D53` alone hits every phone with the Meta app). No signatures for surveillance devices (body cams, smart glasses, ALPR cameras). | open | `android/.../detection/` BLE scanner | Require ≥2 independent fields per rule (OUI + CID, or CID + UUID). Add: AXON body cam (`00:25:DF` + `0x034D` + UUID `0xFC81`/`0xFE6B`/`0xFE6C`), Meta/Ray-Ban glasses (`0x0D53` + `0xFD5F`), Flock ALPR (OUI `b4:1e:52` + probe IE). Run BLE scan ≥90 s to catch devices with extended advertising intervals. Source: OUI-SPY / colonelpanichacks (DEF CON 34, Apache-2.0). |
| 17 | GPS tracker cloud-reported state cannot be trusted. Cloud backends for SETracker / SinoTrack / TKSTAR have BOLA flaws (45 vulns, 9× CVSS 10.0) and an SMS-redirect that lets a stalker reconfigure a tracker to extend its advertising interval or fake absence. | verify | Evidence reports capture interpreted result, not raw RF | Record raw RF observation (payload bytes, RSSI, advertising interval, channel, timestamp) in evidence reports; do not display cloud-reported absent/off as confirmed absence. |
| 18 | Tor fail-open risk: if Tor is unavailable, Clairix may fall back to a direct relay connection. DEF CON 34 Dingledine talk confirmed brief non-Tor connections are the most common deanonymisation cause for Tor-based tools. | verify | Tor connection logic in `android/.../comms/` | Confirm Clairix fails closed when Tor is unavailable and never silently routes relay traffic directly; isolate Tor circuits per conversation; consider onion-service front end to avoid exit-node timing correlation against fixed Cloudflare relay. |
| 19 | Modem resets and forced re-registrations not treated as IMSI-catcher signal. DEF CON 34 baseband research (arXiv 2604.04283) shows pre-authentication 5G crashes via rogue base station look like ordinary signal loss. 64 chipset models affected; MediaTek CVEs patched (CVE-2025-20644, CVE-2025-20703, CVE-2025-20666); Qualcomm still under review. | verify | `android/.../analysis/CellAnalyzer.kt` IMSI-catcher heuristics | Treat unexplained modem resets and forced re-registrations as a corroborating IMSI-catcher signal; surface device security patch level to users and warn when it predates the MediaTek patches; recommend LTE-only mode on GrapheneOS to reduce 5G NR parser exposure. |

## Checked and already covered (not gaps)

- Tapjacking / overlay attacks: `security/WindowShield.kt` (setHideOverlayWindows on API 31+, FLAG_SECURE).
- Cloud backup and device transfer: every data domain excluded.
- Cleartext traffic and CA trust: system-only CA, no cleartext, optional relay-key pinning.
- PendingIntent mutability: 10 `FLAG_IMMUTABLE` hits.
- Exported components: the manifest lines checked show `exported="true"` only on the launcher aliases (MainActivity's own line was not re-read); every other component seen is `exported="false"`.
- Clipboard: sensitive-marked copies, cleared on wipe.
- Reproducible builds: built twice in CI and compared.
