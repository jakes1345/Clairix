# Clairix gap audit: what is missing or wrong (repo at 2b4303a)

The single biggest thing missing is honesty of state: Clairix cannot yet tell a survivor when it has failed, and in every headline path it says the opposite. The SOS button toasts 'sent' before anything leaves the phone and never retries; a scanner silenced by the Location toggle, an app update or one uncaught exception shows a green 'Nothing following'; the hub's 'Phone clear' comes from a stalkerware scan that only runs when its page is opened, against a watch-list that is 14 of 19 invented names; the duress code 'shows nothing unusual' for one shake and then reopens as a blank first run; and every tracker, PIN and sleep-unlock alert prints its full text where the person who planted the tag reads it. The plumbing underneath is genuinely strong (vodozemac E2EE with blind tokens, signed assets and reproducible builds verified on every release, content-neutral Comms notifications, a 1:1 outbox with real back-off, a hardened app lock, honest limits copy in many places), but the verdict layer and the paper around it are not: 'following' is any two fixes 300 m apart with no movement check and every follower is CRITICAL, an open xfinitywifi or your own phone call is 'interception', the GNSS receiver runs a 1 Hz session all day while the website says satellites are off at rest, and the trust pages ('complete list ... Nothing else', 'never a sender', 'exactly one case', 'Panic Wipe in Settings', a Google Play edition, a four-hourly TLS canary) are contradicted by the code in an afternoon's diff. For a buyer the gap is evidence and ownership rather than features: nothing was measured on a device, nobody but the author and the model has read 60k lines written in eleven days, 93 of 159 files are in no test, and there is no legal entity, no second administrator and one relay in a personal Cloudflare account. Roughly half of the top dozen items are hours-sized, so the honest order is stop the lies, then fix the verdicts, then build the evidence.

Method and counts. 14 lanes (trackers, cameras, spyware, networks, survivor UX, trust/acquisition, engineering, compliance, comms/relay, claims-vs-code, Drive/Card Vault/Coin, navigation, emergency features and what the app records, power) produced 191 findings; every one was re-verified against the code by a second agent: 136 confirmed, 55 partially (details corrected), 0 refuted, 0 unverifiable. Evidence is file:line in the repo at 2b4303a. This report merges them into 53 items and 43 one-line entries; every finding id appears exactly once, in the 'ids:' line of one item or one 'Also' entry. Within each section items are ordered by severity, then by effort (cheaper first); effort is for one strong engineer doing the whole merged item.

### 2. GnssMonitor.kt:119 keeps a 1 Hz GNSS session on all day; 'only while you are moving' is false — critical · hours

GnssMonitor.register() (GnssMonitor.kt:108-128) calls registerGnssMeasurementsCallback with no request object, which the android-35 sources build as a default GnssMeasurementRequest with interval 0, 'the fastest rate the chipset can report'; only PASSIVE_INTERVAL costs nothing. Implementation note (2026-11-01), where the fix departs from the Fix paragraph above. GnssMonitor keeps its own NETWORK_PROVIDER request instead of taking the scanner's fused fixes: a fused fix may come from the satellites themselves, so it cannot be the independent position a spoofer is held against. The request is paced instead (GnssRequestPolicy.networkIntervalMs): once a minute with the GPS page open or while moving with satellite fixes arriving, every 15 minutes settled, none after two minutes without a satellite fix. On API 33 and later the measurement request is not passive while the phone moves: a passive request hears only measurements another app asked for, so the gain check had no readings on the move and jamming could not be told from a tunnel; while moving (when the scanner's own fixes have the receiver on anyway) it asks once a second, as API 31-32's default request does, and it is passive (34+) or the longest interval (33) once settled. Still open: the device check (`dumpsys location`, `dumpsys batterystats`) and its CI assertion; the emulator job captures `dumpsys location` after the smoke test but asserts nothing, and the scanner has not settled by then.
